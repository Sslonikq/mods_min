## Задача
Постоянный шаг сборки: все ссылки на классы, методы и поля `net/minecraft*` и `net/minecraftforge*` из `build/classes` проверяются по реальным jar Forge/клиента (имя + дескриптор, с подъёмом по суперклассам).

## Что сделано
- `tools/linkcheck.py` (новый): собственный разбор class-файлов (пул констант) без javap по каждому классу, быстро. Индекс классов строится из jar. Поиск члена идёт по супертипам и интерфейсам. Классы `java/*` (Enum, Object, Record и т.п.) разворачиваются через `javap` (фильтр ложных срабатываний). Цепочка, ушедшая в класс вне найденных jar, считается «не удалось проверить» и не роняет сборку (в статистике).
- Поиск jar: `EW_FORGE_DIR` (список через `os.pathsep`), затем `C:\games\MultiMC\libraries`, `~/.minecraft/libraries`, `~/.gradle`, `.cache` проекта. Берутся forge-*-client / client-*-srg / forge-*-universal / eventbus / fmlcore / javafmllanguage / lowcodelanguage / mclanguage; пропатченный forge-client в приоритете.
- Нет jar (или нет Mojang-путей Minecraft) -> `[2c] linkcheck: НЕ ПРОВЕРЕНО`, сборка не падает. Есть jar и расхождения -> сборка падает со списком.
- `tools/build.py` (CRLF сохранён): шаг `[2c]` после `[2b]`, строка в docstring.
- `CLAUDE.md`, «Команды»: одна строка про `python tools/linkcheck.py`.
- Можно запускать и отдельно: `python tools/linkcheck.py` (код 1 при расхождениях).

## Проверить в игре
Ничего нового; шаг как раз снижает риск `NoSuchMethodError`. Не покрыто: переопределения (сигнатуры наших `m_xxx_` методов относительно родителя), классы не из net/minecraft*/forge (JEI, библиотеки), рефлексия и строки.

## Решения и почему
- Парсер class-файлов вместо `javap -v` по классам мода: на порядок быстрее, не зависит от формата вывода. `javap` остался только для JDK-классов.
- Скрытые падения от разных версий Forge отсеяны: при дублях имён jar берётся самая новая версия.

## Проблемы и открытые вопросы
- `build/` общий для агентов: параллельные запуски `build.py` ломают друг друга.
